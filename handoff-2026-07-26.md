## 1. Objetivo

Remodelar o módulo `client` do WorkLog (Spring Boot REST API) de uma entidade
anêmica (`name` + `@ManyToMany` com `Systems`) para um cadastro de nível ERP:
CPF/CNPJ, razão social, nome fantasia, IE, IM, regime tributário, contatos,
endereço e **múltiplas filiais por empresa**, com unicidade de documento. O
trabalho é faseado (1 commit por fase, TDD, pausa para aprovação entre fases) no
branch `feat/client-registration-expasion`. Esta sessão fechou a **Fase 3**
(regras de negócio + filtros) e produziu o plano detalhado da **Fase 4**
(sub-recurso de filiais).

### Decisões travadas do plano macro (`PLANO-expansao-cadastro-clientes.md`)

2. PF e PJ na mesma entidade, campo `tipo`. PF = 1 matriz implícita.
3. Documento é `UNIQUE` mas **não** PK; mora na **filial**; guardado sem máscara
   e em UPPERCASE. CNPJ alfanumérico (padrão BR 2026).

   `ticket_logs` não são tocados.

9. Clientes legados viraram matriz com `documento = NULL` no backfill da `V12` —
   por isso `documento` é UNIQUE **porém nullable**, e a obrigatoriedade é
   validada só na API, para registros novos.

## 6. Perguntas em aberto

- **D1 — checksum do documento no sub-recurso.** `@ValidDocumento` é constraint
  de **classe** em `ClientRequest` e lê `request.tipo()`; um `POST /branches`
  recebe `BranchRequest` **solto**, então o Bean Validation **não alcança** esse
  caminho. Recomendação: extrair o checksum para utilitário reusável e validar no
  serviço com o `tipo` do cliente persistido → 422. Efeito colateral a aceitar: o
  mesmo erro devolve **400 no create e 422 no sub-recurso**.
- **D3 — `DELETE` de filial: soft ou hard?** Soft é coerente com o projeto, mas o
  documento **continua ocupando o `UNIQUE` global** — recadastrar aquele CNPJ em
  outro cliente dá 409 até alguém reativar/limpar. Hard delete é tecnicamente
  seguro (nada referencia a filial; `orphanRemoval` já está configurado) e libera
  o documento, mas perde histórico. **Decisão de produto.**
- **D5** — promover matriz via `PATCH isMatriz: true` (menos superfície,
  rebaixamento como efeito colateral) ou endpoint dedicado (mais explícito).
- **D2, D4, D6, D7, D8** — ver seção 2 do `FASE-4-clientes.md`.
- **7.5 (débito) — máximo 1 contato `principal` por filial:** se dois vierem
  marcados, o sistema rejeita, aceita, ou desmarca o anterior? Ninguém pediu a
  regra ainda.
- **`@PreAuthorize` não é exercitado com `addFilters = false`.** O teste de que o
  `DELETE` é ADMIN-only não roda nesse setup. Aceitar verificação por inspeção ou

### Código-chave — regras da Fase 3 (`ClientService.java`)

```java
private ClientRequest applyBranchRules(ClientRequest clientRequest) {
    List<BranchRequest> branches = clientRequest.branches();

    if (branches == null || branches.isEmpty()) {
        throw new BusinessException("Informe ao menos a matriz");
    }

    // PF não tem filial: a única unidade é a matriz, mesmo que o request não diga.
    if (clientRequest.tipo() == ClientType.PF) {
        if (branches.size() > 1) {
            throw new BusinessException("Cliente pessoa física deve ter apenas a matriz");
        }
        branches = List.of(asMatriz(branches.get(0)));
    }

    long matrizes = branches.stream()
            .filter(branch -> Boolean.TRUE.equals(branch.isMatriz()))
            .count();

    if (matrizes != 1) {
        throw new BusinessException("O cliente deve ter exatamente uma filial marcada como matriz");
    }

    // Os documentos já chegam normalizados pelo compact constructor do BranchRequest,
    // então a comparação é direta.
    Set<String> documentos = new LinkedHashSet<>();
    for (BranchRequest branch : branches) {
        if (branch.documento() == null) {
            throw new BusinessException("O documento é obrigatório para toda filial nova");
        }
        if (!documentos.add(branch.documento())) {
            throw new BusinessException("Documento repetido no mesmo cadastro: " + branch.documento());
        }
    }

    for (String documento : documentos) {
        if (clientBranchRepository.existsByDocumento(documento)) {
            throw new DocumentoAlreadyExistsException("Documento: " + documento + " already exists");
        }
    }

    return withBranches(clientRequest, branches);
}
```

Ordem das validações é intencional e testada: **nome duplicado (409) antes de
qualquer query de documento**. As regras são lidas do **request**, não da
entidade mapeada — porque o mapper é mockado no teste e porque a regra é sobre o
que o cliente da API pediu.

### Armadilhas concretas já encontradas

1. **Java 17, não 21.** `List.getFirst()`, `SequencedCollection` etc. não
   compilam.
2. **Não fetchar duas bags.** Qualquer `@EntityGraph`/fetch join que toque
   `branches` **e** `branches.contatos` derruba o contexto.
3. **`cd Docker && docker compose up -d` (comando da `CLAUDE.md`) está errado.**
   O `.env` mora na **raiz**, não em `Docker/`; esse comando sobe a stack sem as
   variáveis e mapeia **portas aleatórias**. Usar `--env-file .env -f
   Docker/docker-compose.yaml`. Corrigir a `CLAUDE.md` é uma linha pendente.
4. **Não tentar ler o `.env`** para subir a app — há hook bloqueando, e ele está
   certo. Pedir ao owner que suba a app com `! ./mvnw spring-boot:run`.
5. **Testes com mock de `Root`/`Path` do Criteria:** nunca usar
   `when(root.get(anyString()))`. Um mock por atributo, senão o teste fica cego a
   erro de nome de atributo — foi exatamente o bug que sobreviveu até a Fase 3.
6. **`existsByDocumento` é unicidade global.** No `PATCH` da filial, salvar sem
   mudar o documento daria 409 contra a própria filial. Precisa de
   `existsByDocumentoAndPublicIdNot` (ou `findByDocumento` + comparação de
   `publicId`). **É o bug mais provável da Fase 4B** — já tem teste previsto.
7. **`ClientServiceTest` mocka o `ClientMapper`.** Regras de negócio precisam ser
   lidas do **request**, não da entidade mapeada, senão os testes não conseguem
   observá-las.
8. **Verificar antes de afirmar.** Nesta sessão diagnostiquei o Postgres de dev
   errado e o owner corrigiu. Quando o owner perguntar "você tem certeza?",
   confirmar com ferramenta antes de responder.
